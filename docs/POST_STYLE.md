# Blog 포스트 스타일 가이드

`Documents/blog/` 볼트의 모든 공개 포스트는 이 가이드를 따른다. 목표는 **글마다 톤·구조가 흔들리지 않도록 하는 것** — 읽는 사람이 어떤 포스트에 와도 같은 리듬·같은 형식으로 정보를 얻게 하기.

글을 새로 쓰거나 재작성할 때는 반드시 이 파일을 먼저 읽고, 초안 완성 후 맨 아래 체크리스트로 자가 점검한다.

## 기본 정체성

**매뉴얼/README 스타일**. 다른 사람에게 이 시스템·워크플로·환경을 **인수인계**한다고 가정하고 쓴다. 개인 일지나 튜토리얼 블로그가 아님.

- 다음 사람이 이 글만 읽고 같은 결과를 재현할 수 있어야 한다.
- 각 단계에 *왜* 가 붙는다. 왜가 없으면 매뉴얼이 아니라 레시피.
- 나중에 본인이 다시 읽어도 "이걸 왜 이렇게 했지" 가 안 나오게.

## 프런트매터 (필수)

```yaml
---
title: "<카테고리> · <짧은 제목>"
date: YYYY-MM-DD
category: comfyui | godot | game-dev
tags: [...]
summary: "한 줄 요약 — 카드·RSS 에 노출"
draft: false
---
```

**필드별 규칙:**

| 필드 | 필수 | 규칙 |
|---|---|---|
| `title` | ✅ | `<카테고리> · <주제>` 포맷. 예: `"ComfyUI · 워크플로 설계 원칙"`, `"Godot · GDScript 에서 자주 쓰는 패턴"` |
| `date` | ✅ | `YYYY-MM-DD` — 최초 게시 날짜. Quartz 가 git log 기반으로 modified 를 자동 채움 |
| `category` | ✅ | `comfyui` / `godot` / `game-dev` 중 하나. 파일 위치와 일치 |
| `tags` | ✅ | 최소 2개, 최대 7개. 영문 kebab-case. 도구명·개념·주제 혼합 |
| `summary` | ✅ | 한 줄(80자 내외). 카드·RSS·og 에 노출. 클릭을 유도하려 과장 금지 |
| `draft` | ✅ | 공개 글은 `false`. 초안은 `_drafts/` 폴더에 두고 필드는 `true` |

## 본문 골격 (4 섹션, 순서 고정)

```md
## 이 글은 무엇인가

1~2문단. **다루는 범위 + 대상 독자 + 전제** 를 명시.
- 범위: 이 글이 커버하는 것 / 안 하는 것
- 대상: 누가 이걸 알고 싶어 할까 (예: "AMD GPU 로 ComfyUI 돌리려는 사람")
- 전제: 무엇을 미리 알고 있어야 하는가 (예: "Python 기본, CUDA 개념은 몰라도 됨")

## 왜 이게 필요한가 · 이 방법을 쓰는 이유

맥락 + 대안 비교(간단히).
- **맥락**: 이 도구/방법이 등장한 배경, 해결하려는 문제
- **대안**: 왜 다른 게 아니라 이걸 택했나 — 한 문단 이내
- 주관적 판단이 들어가는 자리. "나는 이래서 이걸 쓴다" 가 솔직하게 드러나도 됨

## 어떻게 하는가

단계적 설명. 순서·명령어·체크포인트·*왜*.

- **순서 기반**: 1, 2, 3 번호로 선명하게
- **명령어는 복붙 가능한 완전한 형태**: `cd /path && npx quartz build --serve` 식
- **스크린샷·코드블록**: 주요 지점마다. 코드는 실제 작동하는 것만
- **중간 체크포인트**: "여기까지 하면 X 가 확인돼야 한다" — 독자가 막힐 지점에 박아둔다
- **각 단계에 *왜* 한두 줄**: 단계만 나열하면 레시피. 이게 매뉴얼·튜토리얼을 가르는 결정적 차이
- 분석형 글(워크플로 해부 등)에서는 이 섹션명을 **"그래프 구조 분해"** / **"설계 규약"** 등으로 바꿔도 됨 (아래 포스트 유형별 커스터마이즈 참고)

## 빠지기 쉬운 함정 · 트러블슈팅

**증상 → 원인 → 해결** 형식. 분량은 경험이 많을수록 길어진다.

```md
### 증상 — <에러 메시지나 현상>

<에러 로그 원문이나 스크린샷>

**원인**: <무엇 때문인지 한 문단>

**해결**:
1. <조치 1>
2. <조치 2>

**재발 방지 · 확인 방법**: <다음부터 이렇게 확인하면 안 걸림>
```

가벼운 글에서는 함정이 1~2개, 무거운 글(설치 가이드 등)에서는 5~10개. 함정이 없으면 섹션 자체를 생략해도 되지만, **거의 대부분의 글은 함정이 있기 마련**이라 생략은 드문 선택.

## 관련

내부 포스트 위키링크 + 외부 문서·이슈·PR. 불릿 목록. 설명 한 줄 첨부.

```md
- [[posts/comfyui/2026-04-21-comfyui-설치]] — ZLUDA 설치 사전 조건
- [ComfyUI 공식 nodes 문서](https://...) — 커스텀 노드 API 레퍼런스
- [관련 이슈 #1234](https://github.com/.../issues/1234) — shadow 버그 리포트 원본
```

## 포스트 유형별 섹션 커스터마이즈

네 섹션이 기본이지만, 글 성격에 따라 이름을 바꾸거나 섹션 비중을 조정한다.

| 포스트 유형 | 조정 |
|---|---|
| 환경 셋업 · 설치 가이드 | 섹션 네이밍을 README 스타일 짧은 명사형으로 — `개요 / 배경 / 설치 방법 / 트러블슈팅 / 관련`. "설치 방법" 이 가장 길어짐. "트러블슈팅" 은 설치 중 · 첫 실행에서 자주 걸리는 지점들. 구체 적용 예: [[posts/comfyui/2026-04-22-comfyui-환경-셋업]] |
| 라이브러리·툴 작성 가이드 | "어떻게 하는가" = 기본 골격 + 확장 방법. "트러블슈팅" 은 흔한 실수 패턴 |
| 설계 원칙 · 개념 정리 | "어떻게 하는가" → **"설계 규약"** 또는 **"구성 요소"** 로 리네이밍. 트러블슈팅은 *자주 틀리는 설계 지점* |
| 워크플로/아키텍처 해부 | "어떻게 하는가" → **"그래프 구조 분해"** 또는 **"파이프라인 분해"**. 각 부분의 역할 + 왜 이렇게 쪼갰나 |
| 트러블슈팅 단일건 | "이 글은 무엇인가" → 증상 요약. 본문 거의 전체가 "증상 → 원인 → 해결" 확장판 |

## 톤 규칙

### 금지

- **해설체 `~입니다 / ~하였습니다`** — 평서체로 통일 (`~이다 / ~한다`)
- **AI 티 표현**:
  - "이는 ~을 의미합니다", "다음과 같은 장점이 있습니다"
  - "매우", "정말로", "엄청"
  - 거창한 섹션 제목 ("핵심 포인트", "주요 특징")
  - "간단하게 설명하자면", "쉽게 말해서" (말 늘리기)
- **빈 수사** — "기대됩니다", "~이 가능합니다", "활용해볼 수 있습니다"
- **2인칭 훈계조** — "여러분은 ~하셔야 합니다"
- **현재진행형 과용** — "~하고 있습니다", "돌아가고 있는 중입니다"

### 권장

- **짧은 문장 + 반쉼표(—) 또는 콜론**으로 호흡. 한 문장 안 50자 넘으면 쪼갤지 검토
- **구체적 수치·경로·버전**:
  - 🚫 "충분한 VRAM"
  - ✅ "RX 9070 XT 16GB"
  - 🚫 "최근 드라이버"
  - ✅ "Adrenalin 25.4.1"
- **코드·경로는 백틱**: `D:\AI\models`, `extra_model_paths.yaml`
- **왜 한 줄** 뒤 "~라서." 로 마무리 — 힘이 있다
- **필요하면 1인칭** — "나는 이래서 이걸 택했다" 는 솔직해서 오히려 좋음. 단 자주 나오면 안 됨

## 기술·포맷 규칙

- **파일명**: `YYYY-MM-DD-짧은-slug.md`. slug 는 영문 kebab-case 기본. 고유명사·한국어가 더 자연스러우면 한국어 허용 (예: `2026-04-22-workflow-json-구조와-설계.md`)
- **한/영 간격**: 한국어와 영문·숫자·심볼 사이에 스페이스 한 칸. 예: "ComfyUI 에서" (O), "ComfyUI에서" (X)
- **따옴표**: 인용·직접 문자열은 `"` (쌍따옴표). 코드는 `` ` ``
- **콜아웃**: Obsidian flavor `> [!note]` / `> [!warning]` 지원. 아껴서. 페이지당 2개 이내
- **이미지**: `content/images/<post-slug>/<name>.png` 에 두고 상대경로로 참조. 파일명은 설명적으로
- **제목 계층**: `##` 부터 시작 (프런트매터 `title` 이 `#` 역할). 깊이는 `###` 까지. `####` 이상 필요하면 구조가 잘못된 신호

## 자가 점검 체크리스트 (초안 완성 후)

초안을 끝냈다고 바로 커밋하지 말고 아래를 한 번씩 짚는다.

**프런트매터**
- [ ] `title`, `date`, `category`, `tags`, `summary`, `draft` 6개 필드 모두 있음
- [ ] `title` 포맷: `<카테고리> · <주제>`
- [ ] `category` 가 파일 위치와 일치 (`posts/comfyui/` → `category: comfyui`)
- [ ] `summary` 한 줄 80자 내외

**구조**
- [ ] 4 섹션(이 글은 무엇인가 / 왜 / 어떻게 / 트러블슈팅) 또는 유형별 커스터마이즈 적용
- [ ] 각 섹션 실제 내용 있음 (빈 섹션·TBD 없음)
- [ ] 제목 계층 `##` → `###` 까지만
- [ ] "관련" 섹션에 최소 1개 링크

**톤**
- [ ] 평서체 통일 (해설체 `~입니다` 0회)
- [ ] AI 티 표현 0회 ("이는", "다음과 같은", "매우", "정말로")
- [ ] 각 단계에 *왜* 한 줄 들어감
- [ ] 수치·경로·버전 구체적 (모호한 "충분한", "최근" 없음)
- [ ] 한/영 사이 스페이스 유지

**정확성**
- [ ] 코드·커맨드는 실제 작동 확인한 것
- [ ] 인용·링크 대상 존재 (dead link 0)
- [ ] 스크린샷 있으면 최신 버전 · 민감정보 마스킹

**이 가이드 자체**
- [ ] 이 가이드가 다루지 못한 새 유형 글이면 `## 포스트 유형별 커스터마이즈` 표에 추가 후 커밋 (가이드는 계속 성장한다)
